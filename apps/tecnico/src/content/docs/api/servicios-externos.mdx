El backend usa Redis para habilitar colas BullMQ y Firebase Cloud Messaging (FCM) para push. La disponibilidad de estos servicios no reemplaza los controles de autorización ni garantiza que una notificación sea recibida o leída.

## 1) Redis y BullMQ

Con una `REDIS_URL` válida, `NotificationsModule` registra su cola BullMQ y procesa los envíos de notificaciones de forma asíncrona. Cada trabajo usa hasta 3 intentos con backoff exponencial de 2, 4 y 8 segundos. `queued: true` confirma el encolado, no la entrega a FCM ni la visualización por el destinatario.

Los envíos directo y por instancia pueden usar fallback síncrono cuando Redis o FCM no están disponibles. En producción, `POST /api/v1/notifications/broadcast` falla si la cola no está disponible: el broadcast no se degrada a ejecución síncrona.

```bash
REDIS_URL=redis://default:password@host:port
```

## 2) Firebase Cloud Messaging (FCM)

FCM es el canal push de SACDIA. La bandeja persistente se registra por separado en `notification_deliveries`: la falta de token o de configuración FCM puede omitir el push sin eliminar la entrega de bandeja. Las preferencias se aplican antes de crear ambos canales, excepto para fuentes `admin:*`, que no permiten opt-out.

### Envíos y bandeja

Todos requieren JWT. Los permisos se aplican antes de encolar o ejecutar el envío:

- `POST /api/v1/notifications/send` requiere `notifications:send` y alcance global.
- `POST /api/v1/notifications/broadcast` requiere `notifications:broadcast` y alcance global.
- `POST /api/v1/notifications/club/:instanceType/:instanceId` requiere `notifications:club` y valida `active_assignment`.
- `GET /api/v1/notifications/targets/club` requiere `notifications:club` y devuelve solo destinos de `active_assignment` autorizados.
- `GET /api/v1/notifications/history` devuelve historial paginado: bandeja propia para usuarios regulares y auditoría con alcance para administración.
- `GET /api/v1/notifications/unread-count` devuelve no leídas del usuario autenticado.
- `PATCH /api/v1/notifications/:deliveryId/read` marca una entrega propia como leída; una entrega ajena no es accesible.
- `PATCH /api/v1/notifications/read-all` marca como leídas todas las entregas propias pendientes.

### Preferencias y tokens canónicos

Las rutas de la app móvil son el contrato canónico autenticado:

- `GET /api/v1/users/me/notification-preferences`
- `PATCH /api/v1/users/me/notification-preferences`
- `POST /api/v1/users/me/fcm-tokens`
- `DELETE /api/v1/users/me/fcm-tokens/:tokenId`

El alta de token lo reactiva y reasocia al usuario actual cuando el valor ya existía. Se conservan como máximo cinco tokens activos por usuario. Los errores FCM permanentes dan de baja el token; los transitorios quedan disponibles para reintento. Un cron elimina tokens sin uso durante más de 90 días los domingos a las 03:00.

También existen `GET` y `POST /api/v1/fcm-tokens`, `DELETE /api/v1/fcm-tokens/by-token`, `DELETE /api/v1/fcm-tokens/:id` y `GET /api/v1/fcm-tokens/user/:userId` como rutas de compatibilidad o administración. El último usa guard owner/admin. Estas rutas no reemplazan `/users/me` para el cliente móvil.

```bash
FIREBASE_PROJECT_ID=...
FIREBASE_CLIENT_EMAIL=...
FIREBASE_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----\n"
```

## 3) Sentry

Sentry se inicializa condicionalmente en `src/main.ts` cuando existe `SENTRY_DSN`; el interceptor global solo se activa en ese caso.

```bash
SENTRY_DSN=https://<key>@<org>.ingest.sentry.io/<project>
```

## 4) Health check de dependencias

`GET /api/v1/health` reporta el estado de `database`, `cache`, `fcm` y `sentry`. Un estado de salud no prueba que un push específico haya llegado al dispositivo.
