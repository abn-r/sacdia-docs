El módulo de comunicaciones combina una bandeja persistente por destinatario y la entrega push mediante Firebase Cloud Messaging (FCM). Sirve para los avisos directos, globales y por instancia de club; no convierte el resultado de un envío en una confirmación de lectura ni de entrega en el dispositivo.

## Bandeja persistente

Cada envío visible crea un registro de auditoría y una entrega en `notification_deliveries` para cada destinatario permitido. La bandeja se consulta con `GET /api/v1/notifications/history`, paginada con `page` y `limit` (valor por defecto 20; máximo 100). Para el usuario regular, el historial es su propia bandeja; para roles administrativos es un historial de auditoría sujeto a su alcance, salvo el superadministrador.

La lectura se gestiona sobre la entrega, no sobre el mensaje push:

- `GET /api/v1/notifications/unread-count` devuelve los no leídos del usuario autenticado.
- `PATCH /api/v1/notifications/{deliveryId}/read` marca una entrega propia como leída; una entrega inexistente o ajena devuelve 404.
- `PATCH /api/v1/notifications/read-all` marca como leídas todas las entregas no leídas del usuario autenticado.

La bandeja persistente y el push son canales separados. Si FCM no está configurado o el destinatario no tiene tokens activos, la entrega de bandeja puede existir aunque no haya push. El push es best-effort y no representa una garantía de recepción, visualización ni lectura.

## Preferencias por categoría

Las preferencias canónicas de la app móvil se consultan y actualizan en:

- `GET /api/v1/users/me/notification-preferences`
- `PATCH /api/v1/users/me/notification-preferences`

El contrato expone un interruptor maestro y las categorías `activities`, `achievements`, `approvals`, `invitations` y `reminders`. Una categoría sin fila persistida queda habilitada por defecto (modelo opt-out). Al actualizar en la misma solicitud el maestro y categorías individuales, primero se aplica el maestro y después las categorías indicadas lo sobrescriben.

Las preferencias se evalúan antes de crear la entrega de bandeja y antes de intentar el push. Las fuentes `admin:*` no admiten opt-out, por lo que no quedan filtradas por preferencias. Existen además `GET /api/v1/notifications/preferences` y `PUT /api/v1/notifications/preferences/{category}` para compatibilidad administrativa; la app debe usar el contrato canónico bajo `/users/me`.

## Entrega asíncrona

Los envíos manuales requieren JWT y permisos explícitos:

- `POST /api/v1/notifications/send` requiere `notifications:send` y alcance global.
- `POST /api/v1/notifications/broadcast` requiere `notifications:broadcast` y alcance global.
- `POST /api/v1/notifications/club/{instanceType}/{instanceId}` y `GET /api/v1/notifications/targets/club` requieren `notifications:club` y validan el recurso `active_assignment`.

Cuando Redis y FCM están disponibles, el módulo encola la entrega con BullMQ. Una respuesta con `queued: true` solo confirma que el trabajo se encoló; no equivale a entregado. Los trabajos tienen hasta 3 intentos y reintentos con backoff exponencial de 2, 4 y 8 segundos. Si el broadcast se solicita en producción sin cola disponible, falla en vez de ejecutarse de forma síncrona.

Para envíos directo o por club, el runtime puede usar un fallback síncrono cuando la cola o FCM no están disponibles. Esa degradación no cambia la separación entre persistencia de bandeja y push, ni transforma un resultado técnico en garantía de entrega.

## tokens FCM

Los tokens FCM se administran por dispositivo con el contrato canónico autenticado:

- `POST /api/v1/users/me/fcm-tokens` registra o reactiva un token y lo reasocia al usuario autenticado cuando ya existía.
- `DELETE /api/v1/users/me/fcm-tokens/{tokenId}` desactiva un token propio por su UUID; el valor secreto del token no viaja en la URL.

El backend conserva como máximo cinco tokens activos por usuario y elimina los más antiguos cuando se supera el límite. Solo los errores permanentes de FCM desactivan un token; los errores transitorios se registran para reintento. La limpieza elimina tokens sin uso durante más de 90 días los domingos a las 03:00.

También existen endpoints bajo `/api/v1/fcm-tokens` para compatibilidad y administración (`GET`, `POST`, `DELETE /by-token`, `DELETE /{id}` y `GET /user/{userId}` con guard owner/admin). No sustituyen las rutas canónicas `/users/me` para el cliente móvil.

## Límites operativos

- No hay confirmación de que el sistema operativo haya mostrado el push ni de que el usuario lo haya leído; la lectura se registra únicamente en la entrega de bandeja.
- Los destinos de club están limitados por `active_assignment`; el endpoint de objetivos devuelve solo las instancias autorizadas para el actor.
- La segmentación manual soportada es directo, global y por instancia de club. No se deben inferir segmentos territoriales o por categoría fuera de los permisos y destinos que devuelve el runtime.
