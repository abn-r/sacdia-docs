## Modelo de autorización

SACDIA resuelve autorización en backend con JWT y guards de NestJS. Los clientes consumen el resultado resuelto, pero no son la barrera de seguridad.

Los roles canónicos usan guion, por ejemplo `super-admin`, `assistant-admin` y `deputy-director`. Los permisos siguen el formato `resource:action`, como `roles:read` y `permissions:assign`.

El perfil de autorización expone tres fuentes de grants:

- roles globales;
- la asignación activa de club;
- permisos directos activos del usuario.

```ts
authorization.grants.direct_permissions: string[];
authorization.effective.permissions: string[];
```

`grants.direct_permissions` participa en `effective.permissions`, junto con los permisos de roles globales y los de la asignación de club activa. Para recursos `global`, el guard evalúa únicamente permisos globales y directos; una asignación de club no amplía ese acceso.

## Enforcement fail-closed

`PermissionsGuard` requiere metadatos de permiso y de recurso en cada handler autenticado que lo use. Si falta alguno —salvo una ruta marcada explícitamente como pública o con `@SkipPermissions()`— rechaza la solicitud con `GUARD_RBAC_MISCONFIGURATION`.

Este comportamiento **fail-closed** evita que una ruta autenticada quede abierta por omitir `@RequirePermissions(...)` o `@AuthorizationResource(...)`.

## API administrativa

El prefijo técnico es `/api/v1/admin/rbac`. Las rutas requieren JWT, `AuthorizationResource({ type: 'global' })` y el permiso indicado. Las mutaciones señaladas además exigen el rol global `super-admin`.

### Permisos

| Operación | Ruta | Requisito adicional |
| --- | --- | --- |
| Listar | `GET /api/v1/admin/rbac/permissions` | `permissions:read` |
| Detalle | `GET /api/v1/admin/rbac/permissions/:id` | `permissions:read` |
| Crear | `POST /api/v1/admin/rbac/permissions` | `super-admin` + `permissions:assign` |
| Actualizar | `PATCH /api/v1/admin/rbac/permissions/:id` | `super-admin` + `permissions:assign` |
| Desactivar | `DELETE /api/v1/admin/rbac/permissions/:id` | `super-admin` + `permissions:assign` |

La eliminación es baja lógica. El catálogo se usa tanto por la administración de permisos como por la matriz.

### Roles y matriz de permisos

| Operación | Ruta | Requisito adicional |
| --- | --- | --- |
| Listar roles | `GET /api/v1/admin/rbac/roles?active=true|false|all` | `roles:read` |
| Detalle de rol | `GET /api/v1/admin/rbac/roles/:id` | `roles:read` |
| Crear, actualizar o desactivar rol | `POST/PATCH/DELETE /api/v1/admin/rbac/roles[/:id]` | `super-admin` + `permissions:assign` |
| Agregar permisos | `POST /api/v1/admin/rbac/roles/:id/permissions` | `super-admin` + `permissions:assign` |
| Sincronizar permisos | `PUT /api/v1/admin/rbac/roles/:id/permissions` | `super-admin` + `permissions:assign` |
| Quitar un permiso | `DELETE /api/v1/admin/rbac/roles/:id/permissions/:permissionId` | `super-admin` + `permissions:assign` |

La matriz administrativa es una proyección de los endpoints de lectura de roles y permisos. Sus mutaciones usan las rutas de asociación de rol: `POST` agrega, `PUT` reemplaza el conjunto completo y `DELETE` retira una asociación. El rol `super-admin` está protegido por reglas de escritura del servicio.

### Permisos directos de usuario

| Operación | Ruta | Requisito adicional |
| --- | --- | --- |
| Consultar grants | `GET /api/v1/admin/rbac/users/:userId/permissions` | `permissions:read` |
| Asignar un grant | `POST /api/v1/admin/rbac/users/:userId/permissions` | `super-admin` + `permissions:assign` |
| Revocar un grant | `DELETE /api/v1/admin/rbac/users/:userId/permissions/:permissionId` | `super-admin` + `permissions:assign` |

La interfaz administrativa incluye la gestión de permisos directos. Las mutaciones de permisos directos, de asociaciones rol-permiso y de roles emiten eventos de auditoría de dominio; la consulta de esos eventos sigue el contrato de Audit Logs.

### Asignación de roles a usuarios

Las rutas `GET/POST/DELETE /api/v1/admin/rbac/users/:userId/roles[/:roleId]` consultan o modifican registros de `users_roles`. Exigen el rol global `admin` o `super-admin`, junto con `roles:read` para lectura o `permissions:assign` para mutaciones.

La interfaz administrativa filtra el selector y la visualización a roles con `role_category: "GLOBAL"`. La ruta backend productiva no valida `role_category` del `role_id`: una llamada API directa puede persistir una asociación con otra categoría. La resolución de autorización sólo incorpora roles activos `GLOBAL` como grants globales efectivos, por lo que esa asociación fuera de categoría no aporta permisos globales efectivos.

## Límites del contrato

- `effective.permissions` es el conjunto apto para gating de clientes; el backend vuelve a evaluar permisos y alcance en cada solicitud protegida.
- Un permiso directo no reemplaza reglas de territorio, recurso ni ownership aplicables al handler.
- La matriz no crea un modelo de alcance territorial propio: las rutas continúan usando el recurso `global` y las políticas de backend correspondientes.
